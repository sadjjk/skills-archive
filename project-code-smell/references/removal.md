# 要不要存在：删除与收窄的判定方法

第 8 路扫描 `scan-08-removable` 执行时读本文件；其他扫描的候选要判「删除」或「收窄」时也读本文件。

目标是找出维护成本存在、实际效果不存在的东西：API、字段、状态、配置项、依赖、测试、文档。少而有证据，优先于删得多。

方法来源：DeepSeek Harness 的 [dsh-find-simplifications](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-find-simplifications/SKILL.md)，去掉了该仓库专用的受保护设计和记录流程。

## 一、追完整链路

判「删除」前，每个候选都要追完四段：

| 段 | 要回答 | 常见漏查 |
|---|---|---|
| 产生 | 谁创建、设置或发出这个值 | 构造函数、工厂、反序列化、默认值 |
| 传递 | 经过哪些转换、转发、序列化 | 配置合并与优先级：值被转发了，但在使用前被另一个来源覆盖 |
| 读取 | 谁读取它并据此改变行为 | 分支判断、判别字段的消费方 |
| 效果 | 用户或下游能观察到什么 | 只被日志或测试读取 |

搜索规则：

- 先用 `rg`（没装时用 `grep -rn`）搜精确符号，再读匹配结果。搜索对象包括：符号名、属性读写、字符串字面量（事件名、配置键、路由、序列化字段名）、包名，以及 `.method(` 和 `method(` 两种写法。
- 搜索覆盖全仓库，不受第一步所选范围限制。候选来自所选范围，证明「没人用」要搜全仓库。
- 必查非源码入口：包清单与导出（如 `package.json`、`pyproject.toml`、`go.mod`）、动态加载（反射、插件注册、按字符串导入、`getattr`）、生成产物与代码生成模板、脚本与 CI 配置、部署配置。
- 示例和 fixture 按实际入口分类，不按目录名分类。
- 测试和类型声明能说明存在约定，不能证明有真实的产生方或消费方。

证据强度：

- 「零调用方」是弱证据。公开库的导出、插件扩展点、对外 API 可能被仓库外使用，零调用方也可能是有意保留。
- 「走不到」是强证据：没有任何产生方，或所有实现都拒绝这个值。用真实数据或实际运行核对过的记为 `Measured`，只靠读代码推出的记为 `Observed`。

## 二、找候选的 6 个问题

1. **效果链是否完整？** 一个字段到处复制，可能没有地方设置它、没有地方读它，或所有实现都拒绝它。
   - 例：配置项 `retry_backoff` 被解析并传进三层，最终的客户端从不读取。
2. **这个区分会不会改变使用方的行为？** 多个内部状态可能只对应使用方的一种处理。授权、持久性、归属相关的区分要保留。
   - 例：`PENDING`、`QUEUED`、`WAITING` 三个状态，所有调用方都走同一个分支。
3. **能否用更小的显式行为替代整个子系统？** 写明放弃的能力和删掉的机制。功能有生产调用方时，这是行为决策，归「收窄」，由用户决定。
   - 例：通用 cron 表达式解析只用来表达「每 N 分钟」，可以改为固定间隔。
4. **使用方能否在需要时直接读权威值？** 找复制出来的历史、缓存、失效事件加重读的组合。先确定使用方需要在什么时间点看到这个值。
   - 例：一个持续同步的本地副本，只在用户点击导出时被读一次。
5. **是不是把组合方式当成了策略？** 某个可选服务是否存在、某个方法是否实现，本身就能表达可用性，不需要另建注册表或依赖检查。归属或完成时机不同的操作要保持分开。
   - 例：维护一张「已启用功能」注册表，内容恒等于已安装插件列表。
6. **完整的维护成本归谁？** 把整套被删系统和替代方案（含残留胶水）一起比较。把多余概念挪到离使用方更近的位置，或加检查让两份定义保持一致，都没有减少成本。
   - 例：重复的应用目录、只为解析依赖而存在的子工作区、自带升级流程的安装脚本。

## 三、每个候选要写的内容

| 字段 | 写什么 |
|---|---|
| 调用链 | 产生 → 传递 → 读取 → 效果，每段给 `文件:行号`；缺哪段写明 |
| 删掉什么 | 代码、配置、测试、文档、依赖 |
| 剩下什么 | 删除后仍保留的行为和残留胶水 |
| 损失的能力 | 删除档没有损失写「无」；收窄档必须写具体能力 |
| 保留它的最强理由 | 站在反方，写出最有力的一条 |

结论：

- **删除**：四段链路都已追完，确认走不到、没人读或效果为零。
- **收窄**：有人用，但可以换成更小的行为；是否接受损失由用户决定。
- **保留（受保护）**：项目约束里列出的有意设计。受保护设计内部没人用的成员仍可作为候选，前提是删掉后不影响该设计的目的。
- **保留（证据不足）**：链路没追完，写明缺哪段证据。

## 四、否决条件

满足任一条，就不判删除或收窄：

- 破坏一项必须保留的义务：对外兼容、持久化数据格式、授权、用户可见行为。
- 只是把同样的复杂度挪了位置。
- 没有实质减少：删掉的不多于新增的。

否决按候选逐条判断。一个混合提案中某部分被否，不代表其余独立部分也被否。重新提出被否的候选前，先刷新证据。

## 五、归属和失败语义

- 对复制、冻结、校验和回调捕获：写明值从哪来、下一个归属方是谁、信任边界在哪。同进程的类型化调用通常只读借用；解析器、配置加载、队列、文件、子进程、网络解码要自己持有或校验输入。
- 对异步机制：把每个 promise、标志位、取消路径、清理函数、预留资源对应到它的归属方和状态转换。只有表达同一事实时才合并。
- 必须保留：同步发布与回滚、回调异常隔离、首个终止结果的裁决、进程归属、释放后进入静止状态。
- 持久化的开始/结束记录即使没有渲染方读取，也可能记录真实事实。丢掉中断的工作是能力损失，不是清理冗余日志。

## 六、换成依赖库

只有净减少时才替换：

- 先查现有依赖和语言标准库，再考虑新包。
- 写明替换后能删掉的手写实现和专属测试，以及新包的维护成本和传递依赖。
- 检查最可能让替换失败的差异：协议截断、取消与清理、配置上限、测试时钟、平台打包、源码与构建产物入口。
- 库覆盖了主体逻辑，但胶水代码要重写同样的逻辑才能满足某个上限，这不算简化。
- 不重测库的通用行为，测项目自己的胶水代码。
