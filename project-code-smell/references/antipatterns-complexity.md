# 复杂度坏味道

> 复杂度扫描时读取。

### 复杂度坏味道（算法反模式）

静态复杂度模式是候选项，而非瓶颈的证据。应用**度量优先**原则：

1. 确定实际输入规模、调用频率、I/O 延迟以及路径是否为热路径。
2. 优先使用分析器、代表性基准测试、查询日志、链路追踪或显式操作计数。
3. 仅当工作负载和影响合理时才将候选项提升为发现。
4. 修复后对同一工作负载重新度量；没有基线，不声称性能改善。

对每个复杂度候选项，说明**度量什么**、**何时成为发现**、以及**何时不该标记**。保留以下大 O 分析和正确性检查，但不要仅从语法推断严重程度。

#### 嵌套循环（O(n^2) 及更差）
两个或更多循环相互嵌套，产生多项式复杂度。
- **检测：** `for`/`while` 套 `for`/`while`；`forEach`/`map` 套 `forEach`/`map`；循环内含循环（任意深度）
- **影响：** 双层嵌套 O(n^2)，三层 O(n^3)；中等数据量即爆炸
- **对策：**
  - 为内部集合构建 Map/Set 索引 → O(n+m)
  - 排序 + 双指针 → O(n log n)
  - 迭代前分组/分桶
  - 区间/范围问题用扫描线
- **正确性检查：** 顺序是否重要？是否有重复键？原始逻辑取的是第一个/最后一个/所有匹配？

#### N+1 查询模式
循环体内执行数据库查询、API 调用或 I/O 操作。
- **检测：** `fetch()`/`axios()`/`query()`/`execute()`/`findMany()`/`findOne()`/`findUnique()`/`select()`/`where()` 出现在任意循环结构内
- **影响：** 1 + N 次往返而非 1 次；网络延迟乘以条目数
- **对策：**
  - 按 ID 批量获取：`SELECT * FROM x WHERE id IN (...)` 然后在内存中 join
  - 使用 ORM 预加载 / `include` / `preload` / DataLoader
  - 批量 API 端点接收数组
  - 保留：权限过滤、租户隔离、排序、分页、错误语义
- **正确性检查：** 不要获取原始逐条逻辑不会授权的记录；保留记录缺失时的行为

#### 重复线性扫描（缺少索引）
循环内线性搜索（`includes`、`indexOf`、`.find`、`in_array`），而 Set/Map 可提供 O(1) 查找。
- **检测：** `.includes()` / `.indexOf()` / `.find()` / `.findIndex()` / `in_array()` / `contains()` 出现在循环体内
- **影响：** O(n*m) 而非 O(n+m) — 每次迭代扫描整个集合
- **对策：** 在循环前构建 `Set`（用于成员判断）或 `Map`（用于键→值查找）
- **正确性检查：** Set 转换后等价语义是否变化？JavaScript 对象标识 vs 值相等；Python 可哈希性

#### 循环内排序
循环体内排序，不必要地重复 O(n log n) 工作。
- **检测：** `.sort()` / `sorted()` / `sort()` 出现在任意迭代块内
- **影响：** O(k * n log n) 而非 O(n log n) — 排序重复 k 次
- **对策：**
  - 循环外排序一次
  - 如需增量 top-K 则维护堆（PriorityQueue）
  - 在有序集合中用二分查找/插入
- **正确性检查：** 每个中间排序状态是否外部可见？比较器是否依赖循环局部状态？

#### 渲染路径重复计算（UI 复杂度）
UI 组件渲染体中的高开销数据变换（filter→map→sort 链），每次渲染都重新计算。
- **检测：** `.filter().map().sort().reduce()` 链出现在 React/Vue/Svelte 组件函数体中；出现在 `function Component()` 或 `const Component = () =>` 的 JSX/TSX 中
- **影响：** 即使输入不变，每次状态变更都重新推导；大集合时卡顿
- **对策：**
  - `useMemo` / `computed` / `derived` 配正确的依赖数组
  - 将推导移到选择器、加载器或服务端
  - 长列表虚拟化（窗口化）
  - 仅在子组件渲染受影响时稳定回调和对象 props
- **正确性检查：** 依赖数组必须包含每个语义输入；记忆化不得隐藏可变输入的变更

#### 两两比较
用双层嵌套迭代将每个元素与每个元素比较。
- **检测：** 两个嵌套循环迭代相同或相似集合，比较配对
- **影响：** 配对匹配、重叠检测、冲突检查、最近邻 O(n^2)
- **对策：**
  - 配对/范围匹配用排序 + 双指针
  - 区间重叠用扫描线
  - 邻近问题用空间哈希或网格分桶
  - 连通性用并查集
- **正确性检查：** 顺序稳定性；相等情形的平局处理

#### 不必要重复计算（缺少记忆化）
同一纯计算对相同输入重复执行而未缓存。
- **检测：** 热路径中相同函数对相同参数的相同调用；重复的高开销变换；无记忆化的递归调用
- **影响：** 线性/多项式浪费的工作；递归 Fibonacci 模式尤其严重（O(2^n) → 记忆化后 O(n)）
- **对策：** 添加记忆化/缓存并配正确的失效策略；酌情使用 `lru_cache`/`memoize`/`useMemo`

#### 数据结构不当
为访问模式使用了次优数据结构。
- **检测：**
  - Array/List 用于频繁成员判断 → 应该用 Set
  - Array/List 用于键值查找 → 应该用 Map/Object
  - Array 用 `shift()`/`pop(0)` 做队列（每次出队 O(n)）→ 应该用正经 Queue
  - 有序插入 Array（每次插入 O(n)）→ 应该用 Heap
- **对策：** 替换为复杂度匹配访问模式的数据结构：
  - Set → O(1) has/add/delete
  - Map → O(1) get/set
  - Heap → O(log n) push/pop 用于优先级
  - Queue/Deque → O(1) enqueue/dequeue

#### 不该标记的情况
- **冷路径：** 仅在启动、配置加载或极小 N（< 100）时运行的复杂度很少值得修复
- **有意权衡：** 清晰可读的 O(n) 代码，其中 O(n log n) 会增加复杂度却无可度量收益
- **已优化：** Map/Set 已在使用；批量加载已实现；记忆化已存在
