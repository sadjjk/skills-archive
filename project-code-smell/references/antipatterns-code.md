# 代码、测试与设计原则坏味道

> 模块、模式、测试、命名扫描时读取。

### 代码级坏味道

#### 长方法
- 方法 > 50 行（或视语言而定）
- 嵌套 > 3 层
- 混合多个抽象层次
- **对策：** 在同抽象层次提取方法，组合

#### 长参数列表
- 方法参数 > 4 个
- 布尔标志控制行为
- **对策：** 引入参数对象，拆分方法，移除标志参数

#### 重复代码
- 3+ 处出现相同或近似逻辑
- 复制粘贴略有变化
- **对策：** 提取共享方法，应用模板方法或策略模式

#### 基本类型偏执
用基本类型而非领域类型：
- `string` 用于 Email、PhoneNumber、URL
- `int` 用于 Money、Age、Quantity
- `decimal` 不含 Currency 上下文
- **对策：** 创建带验证和行为的值对象

#### 魔法数字/字符串
- 硬编码字面量无解释
- `if (status == 3)` 而非 `if (status == Status.COMPLETED)`
- **对策：** 提取命名常量或枚举

#### 注释除臭剂
- 注释解释代码做什么（代码应自文档化）
- 被注释掉的代码块
- 「TODO」注释不断累积却不解决
- **对策：** 重构使代码清晰，删除死代码，将 TODO 作为 issue 追踪。删除前按 `references/removal.md` 追完整链路；链路未追完时结论降为「保留（证据不足）」

#### 深层嵌套（箭头反模式）
循环和条件嵌套如此之深，代码向右漂移成「箭头」形状：
- `if { if { for { if { ... } } } }` — 难以追踪任一时刻哪些条件成立
- 一个函数中通常 > 3 层缩进
- **对策：** 卫语句/提前返回，将嵌套块提取为方法，反转条件，用多态替代条件

#### 死代码
- 未使用的 import、变量、函数
- 不可达分支
- 版本控制中被注释掉的代码
- **对策：** 删除（git 历史会保留，需要时可恢复）。删除前按 `references/removal.md` 追完整链路；链路未追完时结论降为「保留（证据不足）」

#### 数据类
只有字段加 getter/setter、无有意义行为的类：
- 一个「数据袋」其他类从外部操作
- 类级别的贫血领域模型
- **对策：** 将操作数据的行为移入类中（「告诉，不要询问」）

#### 冗余类
不再有足够存在价值的类/模块：
- 重构后遗留，或从未成长的抽象
- **对策：** 内联到调用方或合并继承层次。删除前按 `references/removal.md` 追完整链路；链路未追完时结论降为「保留（证据不足）」

#### 投机性泛化
为假设的未来需求添加的抽象、钩子、参数或泛型：
- 未使用的抽象基类、未使用的参数、「以防万一」的配置
- 违反 YAGNI
- **对策：** 移除未使用的抽象；当真实的第二个用例出现时再加。删除前按 `references/removal.md` 追完整链路；链路未追完时结论降为「保留（证据不足）」

#### 临时字段
仅在特定情况下设置/使用、其余时间为空的实例字段：
- 仅在某个算法中填充的字段，在其余时间困扰读者
- **对策：** 将字段和使用它的方法提取到自己的类中（提取类 / 引入方法对象）

### 测试坏味道

#### 无测试
- 模块零测试覆盖
- 业务逻辑无单元测试
- **对策：** 先写特征化测试，再加行为测试

#### 测试-实现耦合
- 测试断言内部方法调用、私有状态或实现细节
- 重构时行为不变但测试失败
- **对策：** 通过公共 API 测试，断言行为而非实现

#### 测试环境依赖
- 测试依赖文件系统、网络、数据库、系统时钟而未模拟
- 不确定性的测试（不稳定测试）
- **对策：** 使用测试替身，控制环境，使用依赖注入

### 设计原则违规

使用 `references/heuristics.md` 中的标准矩阵作为报告契约。这些设计检查细化候选项检测；不按原则逐个创建发现。

- **SOLID 伞形：** 仅当多个 SOLID 关注共享同一根因或更窄视角不可靠时使用。
- **SRP：** 确认独立的变更原因；仅大小不足为据。
- **OCP：** 确认为真实变体反复编辑；不要用投机性多态替代简单的局部条件。
- **LSP：** 子类型必须保持基类契约的前置条件、后置条件和不变量。报告为 `SOLID/LSP`。
- **ISP：** 确认客户依赖了不使用的方法。报告为 `SOLID/ISP`。
- **DIP：** 确认高层策略以妨碍测试或替换的方式耦合到具体机制；单一实现不自动成为加接口的理由。
- **DRY：** 去重共享知识，而非巧合相似的语法。
- **KISS 和 YAGNI：** 拒绝未来变异或杠杆效应未经证明的抽象。
- **组合优于继承：** 当继承暴露不良行为或绑定独立变异轴时优先 — 而非作为机械规则。
- **关注点分离：** 确认策略、表现层、持久化或 I/O 跨越预定边界泄漏。
- **快速失败：** 在无效状态的源头附近检测，同时保留已有的错误、重试、事务和清理语义。
- **度量优先：** 将未度量优化声明降为候选项，而非报告为第二个「原则违规」。

#### 面向对象滥用器（来自 Fowler / refactoring.guru）

##### Switch 语句（类型码条件）
重复的 `switch`/if-else 链按类型码或枚举分支：
- 同一条件结构在多处重复
- 添加新类型需修改每个 switch（违反 OCP）
- **对策：** 用多态替代条件（Strategy/State），或用子类替代类型码

##### 拒绝继承
子类继承了不需要的方法/字段：
- 覆写继承的方法为抛异常、空操作或不相关行为
- 表明继承关系有误
- **对策：** 下推未使用的成员，或用委托替代继承

##### 接口不同的同类类
两个类执行同一角色但方法命名不同：
- `sort()` vs `arrange()`，`getUser()` vs `fetchUser()` 本可互换的类
- **对策：** 统一接口（重命名方法，提取公共父类/接口）

##### 不完整的库类
第三方/库类缺少所需方法且无法修改：
- 围绕库散布辅助函数或复制粘贴包装
- **对策：** 引入外部方法（Foreign Method）或包装为适配器/本地扩展类
