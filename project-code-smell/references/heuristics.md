# 启发式规则与原则矩阵

> 第 1–7 路扫描和发现确认时读取。

### 关键启发式规则

启发式规则是**候选信号，而非发现**。行数、嵌套层级、命名或大 O 表示法的匹配必须结合代码的职责、调用方、变更历史、工作负载和有意约束进行验证。不要仅凭阈值判定严重程度。

| 类别 | 坏味道 | 检测启发式规则 |
|------|--------|---------------|
| **架构** | 大泥球（Big Ball of Mud） | 无清晰目录结构；所有文件堆在根目录或同一个扁平文件夹中；没有关注点分离 |
| **架构** | 违反分层边界 | 内层导入外层；基础设施代码出现在领域/核心层 |
| **架构** | 架构缺失 | 没有 `src/`、`lib/`、`core/` 分离；SQL 内联在 UI 代码中；HTTP 处理器与业务逻辑混杂 |
| **架构** | 分布式单体 | 微服务共享数据库；服务无法独立部署 |
| **架构** | 贫血领域模型（Anemic Domain Model） | 模型/实体类只有 getter/setter 没有行为；所有逻辑都在服务层 |
| **架构** | 不必要的 CQRS | 简单 CRUD 场景使用独立的读/写模型；引入不必要的复杂度 |
| **架构** | 过度分层 | 层次/层级过多，只有传递代码而没有实际价值 |
| **架构** | 过度抽象 | 太多的间接层/接口/泛型，导致代码难以追踪 |
| **架构** | 未来主义架构 | 为可能永远不会到来的需求做投机性灵活性设计（预测未来） |
| **架构** | 技术爱好者架构 | 在生产环境采用炫酷/未经验证的技术，只因新而非因合适 |
| **架构** | 杀鸡用牛刀 | 简单问题套用重量级架构/技术 |
| **架构** | 云端/Visio 架构 | 架构图与实际代码和运行时现实脱节 |
| **耦合** | 循环依赖 | 模块 A 导入 B，B 导入 A；通过导入图分析检测 |
| **耦合** | 内容耦合 | 一个模块直接访问另一个模块的内部/私有成员 |
| **耦合** | 公共耦合 | 过多的全局变量/共享可变状态；单例滥用 |
| **耦合** | 标记耦合 | 只需要几个字段却传递整个数据结构 |
| **内聚** | 上帝对象 | 单个类/模块 > 500 行；> 20 个公共方法；处理不相关的关注点 |
| **内聚** | 霰弹手术（Shotgun Surgery） | 一次变更需要修改 5+ 个不相关模块中的文件 |
| **内聚** | 特性依恋 | 方法调用外部类方法多于自身类方法 |
| **内聚** | 数据泥团 | 同一组 3+ 个参数在多个方法签名中反复出现 |
| **设计** | 抽象泄漏 | 实现细节（数据库查询、HTTP 调用）通过接口暴露 |
| **设计** | 静态粘连 | 过度使用静态方法；静态状态妨碍可测试性 |
| **设计** | 服务定位器滥用 | 传递依赖注入容器而非使用构造函数注入 |
| **设计** | 违反 SOLID 原则 | SRP 违规、OCP 违规（类型判断的 switch/if-else 链）、ISP 违规（臃肿接口） |
| **设计** | Switch 语句 | 同一 `switch`/if-else 链按类型码在多处出现；应使用多态 |
| **设计** | 拒绝继承 | 子类继承了不使用的方法/字段，或覆写后抛异常/空操作 |
| **设计** | 接口不同的同类类 | 两个类做同一件事但方法命名不同 |
| **设计** | 平行继承层次 | 在一个继承体系中创建子类时，被迫在另一个体系中也创建对应子类 |
| **设计** | 投机性泛化 | 未使用的抽象类、钩子、参数或泛型「以备将来之需」（违反 YAGNI） |
| **设计** | 不完整的库类 | 因第三方类缺少所需方法而包装/修补它 |
| **内聚** | 发散性变更 | 一个模块因多种不相关原因被修改（与霰弹手术相反） |
| **内聚** | 数据类 | 只有字段和 getter/setter 没有行为的类（贫血数据袋） |
| **内聚** | 冗余类 | 做得太少、不值得存在的类/模块 |
| **耦合** | 过度亲密 | 两个类互相访问对方私有/内部部分过多 |
| **耦合** | 消息链 | 长调用链 `a.getB().getC().getD()`（违反迪米特法则） |
| **耦合** | 中间人 | 只将每个调用委托给另一个类的类 |
| **代码** | 临时字段 | 实例字段仅在特定情况下设置/使用，其余时间为空 |
| **代码** | 重复代码 | 相同/相似逻辑出现在 3+ 处；复制粘贴模式 |
| **代码** | 长方法 | 方法 > 50 行；嵌套过深（> 3 层） |
| **代码** | 长参数列表 | 方法参数 > 4 个 |
| **代码** | 基本类型偏执 | 用字符串/整数而非领域类型（如 `string email` 而非 `Email` 类型） |
| **代码** | 魔法数字/字符串 | 硬编码字面量未使用命名常量 |
| **代码** | 注释除臭剂 | 用过多注释解释糟糕代码而非重构 |
| **代码** | 死代码 | 未使用的 import、不可达代码、被注释掉的代码块 |
| **测试** | 无测试 | 模块零测试覆盖 |
| **测试** | 测试-实现耦合 | 测试断言内部实现细节而非行为 |
| **测试** | 慢测试 | 测试执行真实 I/O、数据库调用、网络请求而未使用模拟 |
| **命名** | 模糊命名 | `Manager`、`Handler`、`Processor`、`Helper`、`Util`、`Service`、`Data`、`Info` 被过度使用且无上下文 |
| **命名** | 不一致命名 | snake_case 和 camelCase 混用；同一概念使用不同命名模式 |
| **可读性** | 深层嵌套（箭头反模式） | 循环/条件嵌套 > 3 层；右移漂移成「箭头」形状难以追踪 |
| **复杂度** | 嵌套循环（O(n^2)+） | 循环套循环；forEach 套 for；map 套 map；暗示多项式复杂度的嵌套迭代 |
| **复杂度** | 重复线性扫描 | 循环内使用 `includes()`/`indexOf()`/`.find()`；在列表上做 O(n*m) 成员检查而非用 Set/Map |
| **复杂度** | 循环内排序 | 循环体内调用 `.sort()` 或 `sorted()`；排序一次即可却重复 O(n log n) |
| **复杂度** | N+1 查询模式 | 循环内执行数据库/API/HTTP 调用；每次迭代 `fetch`/`query`/`execute`/`findMany` 而非批量 |
| **复杂度** | 渲染路径重复计算 | 组件渲染体中的 `.filter().map().sort()` 链；无记忆化的高开销变换 |
| **复杂度** | 两两比较 | 嵌套迭代将每个元素与每个元素比较；排序+双指针可 O(n log n) 却用了 O(n^2) |
| **复杂度** | 不必要重复计算 | 同一高开销计算重复执行未缓存；缺少 `useMemo`/`memo`/惰性求值 |
| **复杂度** | 数据结构不当 | 用 Array 做 Set/Map 应做的 O(1) 查找；用 List 做本应 Queue/Heap/Stack 的场景 |

### 标准 11 原则矩阵

| 原则 | 确认证据 | 常见误报 / 约束 |
|------|---------|----------------|
| **SOLID** | 设计问题横跨多个 SOLID 视角，或没有更窄的可靠视角 | 不要重复已由 SRP/OCP/DIP 具体发现的条目 |
| **DRY** | 同一业务规则或知识需要多处修改 | 预期独立演化的相似语法 |
| **KISS** | 额外的层、间接或机制增加成本却没有可观察到的杠杆效应 | 消除真实复杂度的小抽象 |
| **YAGNI** | 未使用的扩展点、参数、适配器或投机性需求 | 已有边界或变更所需的、经过测试的接缝 |
| **SRP** | 多个独立的变更原因，由职责或变更历史支撑 | 仅文件大小或方法数量 |
| **开闭原则（OCP）** | 添加已知变体时反复修改稳定的分支逻辑 | 一个简单的局部条件 |
| **依赖倒置（DIP）** | 高层策略直接依赖具体基础设施，妨碍替换或测试 | 为单一稳定实现加接口 |
| **组合优于继承** | 继承导致不良耦合、拒继行为或不可分离的变异轴 | 机械地替换每个有效的继承关系 |
| **关注点分离** | 业务策略、I/O、表现层或持久化关注点跨越边界泄漏 | 有意的薄边界适配器 |
| **快速失败（Fail Fast）** | 无效输入、状态或依赖传播到远处操作才失败 | 有意的聚合、重试或延迟验证语义 |
| **度量优先（Measure First）** | 性能、规模或优化声明缺乏基线或代表性工作负载 | 将静态复杂度报告为已度量瓶颈 |
