# project-code-smell — 代码坏味道与维护负担检测

分析代码库，找出坏味道、反模式、复杂度热点和没有实际效果的维护负担。每条发现先判要不要存在、再判怎么改，结论分删除、收窄、重构、保留四档。

**知识库：** 启发式规则、原则矩阵和反模式目录在 `references/` 下，各扫描按需读取（Fowler / Kent Beck 坏味道目录按 refactoring.guru 分类组织）。

---

## 任务概览

1. 明确范围 — 询问用户要分析项目的哪个部分（整个项目、特定模块、近期变更，或仅找可删除的维护负担）（第一步）
2. 约束确认 — 读项目约束文件，列出不能动的设计，请用户确认并补充（第一步「约束确认」）
3. 使用 `find`、`grep` 和 `Agent`（Explore 子代理）扫描代码库，收集候选信号和证据（第二步）
4. 在确认发现之前，结合上下文、调用方、变更历史、工作负载和度量数据对候选项进行验证；每条先判要不要存在，再判怎么改，给出四档结论之一（删除 / 收窄 / 重构 / 保留）（第三步）
5. 生成详细的 Markdown 报告，保存到本技能目录下的 `tasks/smell-report-[YYYY-MM-DD-HHmm]-[project-name]/` 文件夹（第三步、第四步）
6. 向用户呈现已确认发现和候选项的汇总；默认停在报告，用户说「实施第 N 条」才改文件（第四步）

---

## 第一步：范围确认

询问用户：

```
要分析哪个范围？
  A. 整个项目（全面分析，可能耗时较长）
  B. 特定模块/目录：[请指定]
  C. 仅近期变更的文件（git diff）
  D. 仅架构层面的问题（跳过低层级代码坏味道）
  E. 仅找可删除的维护负担（只跑第 8 路 scan-08-removable）
```

如果用户未指定，不超过 200 个文件的项目默认选 A，超过 200 个文件默认选 C。

### 约束确认

扫描前读项目约束文件，提取有意保留、不能动的设计：

- 读取：`AGENTS.md`、`CLAUDE.md`、`README*`、`docs/`（存在哪个读哪个）；项目本身是 skill 或插件时，它的 `SKILL.md`、`references/` 和对外命令文档也算约束来源
- 提取：写明「有意」「保留」「不要删」「兼容」的设计，对外 API 与扩展点，持久化数据格式
- 把提取结果列给用户确认，并问是否有没写下来的约束
- 用户确认后的清单写入报告「项目约束」一节；清单内的设计本身结论最高为「保留（受保护）」，其内部没人用的成员按 `references/removal.md` 仍可作为候选

没有任何约束文件时，直接问用户有哪些设计不能动。用户说不清时，把对外 API、命令行参数、持久化数据格式默认当作受保护，并在「项目约束」里注明是默认推定。

## 第二步：证据收集

**使用 Explore 子代理**（`Agent` with `subagent_type: "Explore"`）扫描代码库中的架构模式和反模式。并行运行多个探索任务。环境里没有这个工具时，用可用的子代理工具，或由单个代理按顺序跑完各路：

### 探索命令

并行执行以下任务以高效收集证据：

1. **项目结构扫描：** 映射目录树，识别架构风格（分层、模块化单体、微服务等）
2. **依赖分析：** 查找 import/include 模式，检测循环依赖，识别耦合热点
3. **模块/组件扫描：** 识别上帝对象（God Object，文件 > 500 行），检查内聚性，检查单一职责违规
4. **模式检测：** 查找已知反模式特征（静态粘连、服务定位器滥用、抽象泄漏）
5. **测试扫描：** 检查测试覆盖模式、测试文件位置、测试与代码比例
6. **命名与清晰度扫描：** 标记误导性命名、过于泛化的名称（Manager、Helper、Util）、不一致的命名约定
7. **复杂度扫描：** 检测算法复杂度热点 — 嵌套循环、N+1 查询、重复扫描、循环内排序、渲染路径中的重复计算
8. **可删除扫描（`scan-08-removable`）：** 先读 `references/removal.md`，按其中 6 个问题找没有实际效果的 API、字段、状态、配置项、依赖、测试和文档；每个候选追完整链路，搜索覆盖全仓库

范围选 E 时只跑第 8 路。

**前 7 路的轻量查：** 建议重构前，先用 `rg`（没装时用 `grep -rn`）查一次该对象的调用方。查到调用方才给重构建议；查不到时转给第 8 路追完整链路；第 8 路也查不清时，在发现里标「未验证是否需要」。

### 每路扫描要读的文件

| 扫描 | 读取 |
|------|------|
| 1 结构、2 依赖 | `references/heuristics.md`、`references/antipatterns-architecture.md` |
| 3 模块、4 模式 | `references/heuristics.md`、`references/antipatterns-architecture.md`、`references/antipatterns-code.md` |
| 5 测试、6 命名 | `references/heuristics.md`、`references/antipatterns-code.md` |
| 7 复杂度 | `references/heuristics.md`、`references/antipatterns-complexity.md` |
| 8 可删除 | `references/removal.md`、`references/heuristics.md`（确认发现时用其中矩阵） |

启发式规则是候选信号，而非发现，判定方法见 `references/heuristics.md`。

## 第三步：报告生成

### 发现的标识与证据

对每个候选项分三阶段处理：

1. **候选检测：** 静态模式、文件指标和依赖扫描仅产生候选项。
2. **上下文验证：** 阅读实现和相关调用方；检查变更频率、输入规模、运行时频率、框架约束、生成/第三方代码状态以及已有的缓解措施。
3. **发现确认：** 将根因相同、受影响路径相同、失败/变更场景相同、修复方向一致的候选项合并为一个发现。

按独立根因计数发现，而非按涉及的原则数量。使用一个**主要原则**和可选的**相关原则**。`SOLID` 是伞形标签；当证据支持更具体的视角时，使用 `SRP`、`OCP` 或 `DIP` 作为主要标签，且不再创建单独的 SOLID 发现。

标准 11 原则矩阵见 `references/heuristics.md`，确认发现时按其中「确认证据」与「常见误报」判断。

对于每个已确认的发现，单独记录证据强度（`Measured`（已度量）、`Observed`（已观察）或 `Inferred`（已推断）），与置信度（`High`（高）、`Medium`（中）或 `Low/Candidate`（低/候选））分开。证据强度不隐含严重程度。

### 结论档位

发现确认时先判要不要存在，再判怎么改。每条发现只给一个档位：

| 档位 | 条件 | 评严重程度 |
|------|------|-----------|
| **删除** | 没人读、走不到或效果为零，且按 `references/removal.md` 追完完整链路 | 是 |
| **收窄** | 有人用，但可换成更小、更明确的行为；写明损失的能力，由用户决定是否接受 | 是 |
| **重构** | 需要存在，但写法有问题 | 是 |
| **保留** | 「约束确认」清单内的设计（受保护），或证据不足 | 否 |

- **降级规则：** 想判「删除」但链路没追完时，只能判「保留（证据不足）」，并写明缺哪段证据。
- **判定顺序：** 同一对象既像可删又像该重构时，先按删除、收窄判；确定需要存在，才给重构建议。
- **档位与严重程度分工：** 档位决定做什么，严重程度决定先后。

### 严重程度评级

- **严重：** 正确性、可靠性、安全性、数据一致性或已度量的系统级影响；通常需要高置信度。
- **警告：** 明确的影响范围或反复的变更/运行时成本，且具有具体的维护或运行时后果。
- **建议：** 局部的、低频的或有限影响的改进，且有证据。
- **需度量的候选项：** 影响未知的静态信号；不计入严重程度汇总，放入报告的独立部分。
- **保留档不评严重程度：** 结论为「保留」的条目只记原因（受保护 / 证据不足），不计入严重程度汇总。

按 `references/report-template.md`「报告结构」生成报告。

## 第四步：保存与呈现

将报告保存到本技能目录（本 SKILL.md 所在目录，不是当前工作目录，也不是被扫描项目）下的 `tasks/smell-report-[YYYY-MM-DD-HHmm]-[project-name]/` 文件夹，各项目报告集中在一处，不往被扫描仓库或工作目录里写文件。文件夹内包含 `summary.md`（汇总报告）和各路扫描结果文件：`scan-01-structure.md`、`scan-02-dependencies.md`、`scan-03-modules.md`、`scan-04-patterns.md`、`scan-05-tests.md`、`scan-06-naming.md`、`scan-07-complexity.md`、`scan-08-removable.md`，只写实际跑了的那几路。每个扫描文件记录候选信号、验证过程和结论，确认的发现再汇总进 `summary.md`。向用户呈现简要摘要。

摘要格式见 `references/report-template.md`「报告输出示例」。

**执行边界：** 默认只出报告，不改被扫描项目的文件。用户明确说「实施第 N 条」时才动手（N 是报告「详细发现」里的全局编号）：先改一处，即这条发现里的一个修改位置，给用户看效果，确认后再改这条发现的其余位置（包括引用它的文档和测试）和同类位置。删除档每改完一条，重跑该条调用链里的搜索，确认没有遗漏的引用。

## 反模式知识库

按主题分在三个文件，各扫描按「每路扫描要读的文件」读取：

- `references/antipatterns-architecture.md`：架构反模式、十大软件架构错误、耦合与内聚坏味道
- `references/antipatterns-code.md`：代码级坏味道、测试坏味道、设计原则违规
- `references/antipatterns-complexity.md`：复杂度坏味道（算法反模式）

## 边界情况与兜底

| 场景 | 处理方式 |
|------|---------|
| 项目无清晰架构 | 报告「大泥球」并附证据，建议增量重构 |
| 空仓库/monorepo | 报告架构分析需要代码；请用户指定模块 |
| 不支持的语言 | 报告通用结构性观察；注明语言特定检查受限 |
| 报告文件路径冲突 | 文件名追加 `-2`、`-3` 等 |
| 用户想快速检查 | 仅运行严重级别扫描，跳过代码和命名类别 |
| 用户只要一个类别 | 聚焦该类别分析，跳过其他 |
| 用户要求直接删除 | 先出报告；按「实施第 N 条」逐条执行，先改一处看效果 |
| 只扫了部分范围却要判删除 | 证明「没人用」的搜索覆盖全仓库，不受所选范围限制 |
